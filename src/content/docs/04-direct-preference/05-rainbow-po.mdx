## 알고리즘 이름보다 구성 요소

선호 최적화 방법은 피드백 형식, 손실, 길이 정규화, 참조 모델, 데이터 수집 방식이 다르다. 이름이 다르다고 모든 구성 요소가 새로운 것은 아니다. 같은 모델·자료·예산에서 구성 요소를 하나씩 비교해야 한다.

## RainbowPO의 실제 분류

[RainbowPO](https://arxiv.org/abs/2410.04203)는 여러 DPO 계열 방법을 일곱 축으로 정리하고 하나의 목적식 안에서 조합한다.

| 축 | 확인할 선택 |
|----|-------------|
| 길이 정규화 | 합 로그 확률 또는 길이 평균 |
| 링크 함수 | logistic·hinge·제곱 손실 |
| Home advantage | 선호 응답에 대한 목표 마진 |
| 참조 정책 | SFT 참조 또는 참조 없는 구성 |
| 문맥별 스케일링 | 문제·응답별 가중치 |
| Rejection sampling | 자료 분포를 바꾸는 선별 |
| SFT 손실 | 선호 응답 우도 항의 결합 |

논문은 이 축들의 실험과 결합을 연구한다. "부정적 기울기 방지"라는 임의의 네 번째 기법이나 모든 태스크의 최고 성능을 보장하는 알고리즘으로 설명하지 않는다.

## 피드백 형식과 온라인 여부

DPO·IPO·ORPO·SimPO는 주로 선호 쌍을 사용하고, KTO는 개별 응답의 좋음·나쁨 레이블을 사용한다. 피드백 형식과 새 데이터를 생성하는지 여부는 다른 축이다.

RLVR이나 DAPO는 온라인 정책 최적화에 속한다. 직접 선호 최적화의 변형 목록에 이름만 섞어 넣지 않는다. 같은 시스템에서 결합할 수 있다는 점과 같은 알고리즘 계열이라는 점은 다르다.

## 구현 지원과 논문 기여

논문이 남아 있어도 라이브러리 구현은 제거될 수 있다. [TRL v1.14.0](https://github.com/huggingface/trl/releases/tag/v1.14.0)은 실험용 BCO·PRM·GSPO-token 등의 제거를 명시한다. 이름이 문헌 목록에 있다는 이유로 현재 트레이너를 import할 수 있다고 가정하지 않는다.

현재 구현을 고를 때는 설치한 릴리스, 데이터 형식, 지원 손실, 참조 모델 처리 방식을 확인한다. 다른 라이브러리의 같은 이름도 실제 목적식과 기본값을 비교한다.

## 선택과 실험

| 제약 | 검토할 방법 | 남는 과제 |
|------|-------------|-----------|
| 비교 쌍이 부족함 | KTO 등 이진 피드백 | 레이블 품질·균형 |
| 참조 모델 비용 | SimPO·ORPO 또는 참조 점수 사전 계산 | 길이·마진·SFT 항 |
| 선호 마진 과최적화 | IPO 등 유한 목표 | 검증 성능·실제 KL |
| 여러 변경 결합 | RainbowPO 방식의 구성 비교 | 요소별 절제 실험 |

알고리즘 선택을 성능 순위로 고정하지 않는다. 검증 자료와 독립 평가를 먼저 정하고, 학습 손실이 아닌 실제 목표의 변화를 비교한다.
