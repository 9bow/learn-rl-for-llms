## 에이전트 RL의 단위는 궤적이다

단일 응답 RL에서는 프롬프트와 완성문 하나를 비교하면 됩니다. 에이전트는 관찰, 도구 호출, 환경 반응, 다음 행동이 이어지는 궤적을 만듭니다. 보상은 마지막 성공 여부만이 아니라, 어떤 초기 상태·권한·도구 버전에서 실행됐는지와 함께 해석해야 합니다.

```text
초기 상태 s₀ → 관찰 o₀ → 행동 a₀ → 환경 상태 s₁
                                   │
                                   ▼
                         … 반복 … → 최종 검증기
                                                   │
                                      성공/실패와 실행 영수증
```

## RAGEN이 보여 주는 긴 궤적 문제

[RAGEN](https://arxiv.org/abs/2504.20073)은 멀티턴 에이전트 RL에서 긴 지평, 확률적 환경 반응, 보상 분산이 함께 나타남을 분석합니다. 최종 보상만 쓰면 어느 도구 호출이나 추론 단계가 결과에 기여했는지 알기 어렵습니다. 이 때문에 환경을 작게 나누고, 상태 다양성을 확보하며, 중간 검증 신호를 신중히 설계해야 합니다.

중간 보상은 만능이 아닙니다. 파일을 열었거나 도구 호출 문법이 맞았다는 점수는, 작업을 실제로 해결했다는 보상과 다릅니다. 각 보상은 최종 성공과의 관계를 표본으로 점검하고, 모델이 형식만 최적화하는지 관찰해야 합니다.

## 비동기 롤아웃과 정책 최신성 저하

대규모 시스템은 생성기와 학습기를 병렬로 돌려 장치 유휴 시간을 줄입니다. 생성기가 이전 정책으로 만든 궤적을 학습기가 받는 동안 정책은 이미 바뀔 수 있습니다. 이 차이를 **정책 최신성 저하(policy staleness)** 라고 하며, 온폴리시 알고리즘의 가정을 약화시킬 수 있습니다.

| 선택 | 이점 | 점검할 위험 |
| --- | --- | --- |
| 동기식 롤아웃 | 정책 일치가 명확함 | 생성 대기 시간 |
| 비동기식 롤아웃 | 처리량 증가 | 오래된 궤적·오프폴리시 편향 |
| 체크포인트 혼합 | 탐색 다양성 | 어떤 정책이 만든 데이터인지 추적 필요 |

실무에서는 각 궤적에 정책 버전, 환경 버전, 도구 출력, 검증 결과를 남기고 허용 가능한 지연 범위를 정합니다. 중요도 보정이나 오래된 궤적 폐기는 가능한 대응이지만, 어떤 방법도 검증 없는 처리량 수치보다 우선하지 않습니다.

## 정리

에이전트 RL 시스템을 비교할 때 특정 벤치마크 점수만으로 일반화를 주장하면 안 됩니다. 환경 계약, 상태 초기화, 검증기, 정책 버전, 롤아웃 보관 방식을 함께 공개해야 학습 결과를 재현하고 안전하게 해석할 수 있습니다.
