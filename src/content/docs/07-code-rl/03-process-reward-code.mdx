## 결과와 과정의 구분

결과 보상은 완성된 코드의 테스트 결과를 평가한다. 과정 보상 모델(PRM)은 생성 중간 단계에 점수를 준다. 테스트 통과율 같은 결과 보상도 연속값일 수 있으며, 결과 보상이 반드시 0/1인 것은 아니다.

코드 생성의 단계는 토큰, 줄, 논리 블록, 함수로 정의할 수 있다. 단계 경계를 정했다고 그 단계의 정확성을 자동으로 증명할 수 있는 것은 아니다. 함수 간 의존성과 아직 작성하지 않은 부분을 고려해야 한다.

## 코드 PRM의 실제 연구

[Process Supervision-Guided Policy Optimization for Code Generation](https://arxiv.org/abs/2410.17621)은 줄 수준의 밀집 피드백을 연구한다. PRM을 단계별 보상으로 쓰는 방법과 가치 함수 초기화에 쓰는 방법을 비교한다.

PRM 점수로 좋은 경로를 더 자주 선택하도록 학습할 수 있다. 다만 잘못된 PRM 점수도 정책에 반복 전달된다. 독립 테스트와 PRM의 오류율을 함께 측정해야 한다.

## ThinkPRM의 위치

[ThinkPRM](https://arxiv.org/abs/2504.16828)은 검증용 추론을 생성하는 PRM이다. 주된 과정 감독 자료는 수학 추론이다. ProcessBench의 오류 탐지와 MATH-500·AIME의 후보 선택·탐색을 구분하여 평가한다.

논문은 GPQA-Diamond 일부와 LiveCodeBench의 분포 외 평가도 수행한다. 이를 모든 코드 단계에 대한 정확한 판정이나 전용 코드 PRM의 보장으로 해석하지 않는다. 생성적 검증도 환각·길이 편향·보상 해킹에 취약하다.

## 함수 단위 보상의 설계 예시

다음은 특정 논문의 알고리즘이 아니라 교육용 설계다. 함수를 개별 테스트로 검사하고, 전체 프로그램 테스트를 별도로 둔다.

```text
함수 작성 → 함수 단위 테스트 → 중간 점수
함수 결합 → 통합 테스트 → 최종 결과 점수
점수와 실행 추적 저장 → 정책 업데이트 또는 후보 선택
```

함수 점수만 최대화하면 인터페이스가 맞지 않는 함수들의 조합이 생길 수 있다. 중간 점수의 합이 최종 정답성을 대신하지 않도록 설계한다.

## PRM을 적용할 때 확인할 항목

| 항목 | 질문 |
|------|------|
| 단계 정의 | 줄·블록·함수 중 무엇을 평가하는가? |
| 감독 자료 | 실행, 인간 주석, 모델 판정 중 무엇인가? |
| 독립 평가 | 학습에 공개하지 않은 테스트가 있는가? |
| 누출 | PRM 입력에 정답 패치나 비공개 테스트가 섞이는가? |
| 비용 | 단계 수와 검증 토큰이 늘 때 비용은 얼마인가? |

과정 보상은 신용 할당을 세밀하게 만들 수 있다. 그러나 테스트 통과나 논리적 정확성을 보장하지 않으며, 충분한 결과 검증과 함께 사용해야 한다.
