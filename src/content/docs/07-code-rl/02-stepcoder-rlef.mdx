## 실행 피드백과 탐색

코드를 처음부터 끝까지 생성한 뒤 최종 테스트만 평가하면 긴 프로그램의 탐색이 어렵다. StepCoder는 완료해야 할 코드 범위를 조절하고, RLEF는 실패 후 실행 피드백을 활용하는 행동을 학습한다.

## StepCoder의 CCCS

[StepCoder](https://arxiv.org/abs/2402.01391)의 CCCS는 `Curriculum of Code Completion Subtasks`다. 정답 프로그램의 일부 접두사를 제공해 나머지를 완성하게 하고, 점차 모델이 생성해야 하는 부분을 늘린다. 마지막에는 문제 설명만으로 전체 코드를 생성한다.

```text
초기: 긴 정답 접두사 + 짧은 나머지 생성
중기: 더 짧은 접두사 + 더 긴 나머지 생성
후기: 문제 설명 + 전체 코드 생성
```

이 과정을 임의의 $O(L/k)$ 복잡도 개선 법칙으로 표현할 수는 없다. 어려운 긴 탐색을 더 쉬운 완료 문제로 나누는 커리큘럼이다.

## FGO의 실제 마스크

FGO는 `Fine-Grained Optimization`이다. 테스트 실행에서 실행하지 않은 코드 구간을 정책 손실에서 제외한다. 오류 행 이후를 모두 마스킹하는 알고리즘이 아니다.

실행된 코드도 기능적으로 틀릴 수 있다. 마스크는 어떤 코드가 보상 계산에 관여했는지를 반영하며, 올바른 줄만 식별하는 검증기는 아니다.

APPS+는 잘못된 프로그램·입출력 형식 등을 정제하고 테스트를 수동 확인한 자료다. 원 APPS에 임의의 수만큼 테스트·중간 점수를 추가한 표로 설명하지 않는다. 공개 데이터의 실제 분할을 따른다.

## RLEF: 여러 시도의 피드백 활용

[RLEF](https://arxiv.org/abs/2410.02089)는 생성 코드의 실행 피드백을 다음 시도의 입력으로 활용하는 능력을 RL로 학습한다. 같은 예산의 독립 샘플링과 반복 수정도 비교해야 한다.

논문은 경쟁 프로그래밍 과제에서 8B·70B 모델을 평가한다. 다른 CodeLlama 7B·34B의 임의 HumanEval·MBPP 표를 그 논문의 결과로 붙이면 안 된다. 테스트 결과뿐 아니라 오류 설명과 이전 코드가 후속 행동의 관측이 되는 점이 핵심이다.

## 과정 감독과의 연결

[Process Supervision-Guided Policy Optimization](https://arxiv.org/abs/2410.17621)은 줄 수준의 밀집 과정 피드백과 가치 초기화를 연구한다. 이를 근거 없이 CodePRM이라는 별도 Generate-Verify-Refine 논문으로 바꾸어 소개하지 않는다.

| 접근 | 학습에서 바꾸는 것 |
|------|--------------------|
| StepCoder CCCS | 생성해야 할 코드의 길이·난이도 |
| StepCoder FGO | 실행한 코드 구간의 손실 마스크 |
| RLEF | 실행 피드백을 받은 후의 수정 행동 |
| 코드 PRM | 단계별 점수와 가치 초기화 |

## 평가 조건

프로그램 생성·수정 횟수, 총 생성 토큰, 공개 테스트와 비공개 테스트를 함께 기록한다. 컴파일 실패·테스트 실패·환경 장애를 구분하고, 실행 예산을 맞춘 뒤 실제 최종 정답률을 비교한다.
