## 함수 정답에서 저장소 작업으로

코드 RL의 초기 과제는 함수 하나를 생성하고 단위 테스트를 통과시키는 형태가 많았습니다. 이 보상은 명확하지만, 실제 소프트웨어 작업은 이슈를 읽고 관련 파일을 찾고 패치를 만들며 회귀를 막는 과정입니다. 따라서 저장소 수준 RL에서는 최종 코드 문자열이 아니라 **격리된 실행 환경에서 검증한 패치**를 보상 단위로 삼아야 합니다.

```text
이슈 + 저장소 스냅샷
          │
          ▼
 [에이전트 궤적: 탐색 → 수정 → 테스트]
          │
          ▼
 [격리된 하니스: 빌드·테스트·패치 검사]
          │
          ├── 통과 ──► 양의 보상 후보
          └── 실패 ──► 실패 유형을 포함한 피드백
```

## SWE-bench가 제공하는 검증 단위

[SWE-bench](https://github.com/SWE-bench/SWE-bench)는 실제 GitHub 이슈와 해당 시점의 코드베이스를 연결하고, 생성 패치를 컨테이너에서 평가합니다. `SWE-bench Verified`는 사람이 해결 가능성을 확인한 500개 문제로 구성됩니다. 여기서 중요한 점은 리더보드 수치 자체가 아니라, **데이터셋·이미지·평가 하니스 버전을 함께 고정해야 결과를 재현할 수 있다**는 점입니다.

| 층 | 확인할 것 | 보상 설계의 위험 |
| --- | --- | --- |
| 구문 | 파싱·컴파일 | 컴파일만 되는 무의미한 패치 |
| 단위 테스트 | 표적 동작 | 공개 테스트에만 과적합 |
| 회귀 테스트 | 기존 동작 | 실행 시간이 길고 불안정함 |
| 패치 검토 | 변경 범위·보안 | 테스트가 놓친 부작용 |

## 검증기를 학습 환경으로 설계하기

검증기는 단순한 `pass/fail` 함수가 아닙니다. 실행할 명령, 네트워크 차단, 시간·메모리 한도, 파일 쓰기 범위, 의존성 버전이 모두 보상 함수의 일부입니다. 예를 들어 테스트가 외부 네트워크에 의존하면 같은 패치도 다른 보상을 받을 수 있습니다. 학습과 평가는 다음을 기록해야 합니다.

1. 저장소 커밋과 데이터셋 리비전
2. 컨테이너 이미지와 테스트 명령
3. 타임아웃·재시도·캐시 정책
4. 패치, 에이전트 궤적, 표준 출력과 오류 출력

이 기록은 “점수가 높다”는 주장보다 중요합니다. 재현 가능한 실패 사례가 있어야 보상 해킹, 하니스 오류, 실제 개선을 구분할 수 있습니다.

## RL에 사용할 때의 주의점

코드 실행은 비용이 크고 실패 원인이 다양합니다. 컴파일 실패·테스트 실패·환경 실패를 같은 0점으로 합치면 신용 할당이 약해집니다. 반대로 지나치게 세밀한 중간 보상은 모델이 테스트 호출 수나 형식만 최적화하게 만들 수 있습니다. 안전한 기본값은 최종 테스트 통과를 주 신호로 두고, 중간 신호는 디버깅용 관찰값으로 별도 기록하는 것입니다.

또한 학습에 쓴 이슈·테스트가 평가에 섞이면 성능은 실제 일반화보다 높게 보입니다. 학습·검증·평가 저장소와 시간 기준을 분리하고, 숨은 테스트를 우회하는 패치가 없는지 표본 검토해야 합니다.

## 정리

코드 RL의 핵심은 특정 모델이나 점수가 아니라 검증 가능한 실행 환경입니다. 함수 수준 테스트는 빠른 학습 신호를, 저장소 수준 하니스는 실제 작업과 가까운 보상 신호를 제공합니다. 두 수준을 섞되, 모든 실행 조건과 패치를 함께 남겨야 결과를 비교할 수 있습니다.
